# Naviora 自定义域名支持方案

## 1. 文档目的

这份文档用于明确 Naviora 后续支持“用户绑定自定义域名”的最终方向，并把之前偏复杂的 `go + page` 双 surface 设计正式收口。

当前结论已经确定：

- 不做 `page` 自定义域名
- 不做 `page.naviora.link` 这类独立内容域名方案
- 自定义域名只支持 `go` 入口域名
- 自定义域名首发和后续一段时间内统一使用 `/l/:slug`
- 其他路径前缀不是当前域名能力的一部分，等 `/l` 真不够用时再单独启用

这是一份“收口后的执行方案”，不是讨论稿。

---

## 2. 最终架构决策

### 2.1 只保留一种自定义域名

后续用户可绑定的自定义域名，统一定义为：

- `go` 入口域名

例如：

- `go.brand.com`
- `qr.brand.com`
- `link.brand.com`

不再支持：

- `page` 内容域名
- `card.brand.com`
- `page.brand.com`
- “同一客户同时配置 go 域名 + page 域名”的产品模型

### 2.2 只保留一种官方生成路径

自定义域名下的正式公开链接，统一生成：

- `https://{custom_domain}/l/:slug`

当前不进入自定义域名能力范围的路径包括：

- `/c/:slug`
- `/s/:slug`
- 其他未来内容模块路径

说明：

- 现有系统内如果还保留 `/c`、`/s` 等兼容路由，那只是历史兼容能力
- 它们不是自定义域名的首发路径策略
- 后续若确实需要更多路径前缀，应作为单独版本重新评估

### 2.3 Preview 继续使用系统域名

Preview 不走用户自定义域名。

继续使用：

- `https://go.naviora.link/preview/:token`

原因：

- Preview 是未发布状态
- 避免客户在 DNS、证书未完成时遇到异常
- 避免把草稿链接暴露在客户品牌域名上

---

## 3. 为什么要这样收口

### 3.1 `page` 域名没有继续存在的价值

既然已经确认 `page` 域名后续不会启用，那么围绕它保留的数据模型、后台交互、路由判断和产品说明，只会制造额外复杂度：

- 让用户误以为以后还能绑定第二类域名
- 让开发在实现时多维护一套无效分支
- 让运行时 host 解析多一层没必要的判断
- 让链接生成策略出现两套口径

因此这里不做“先保留、以后再说”，而是直接从方案层移除。

### 3.2 `/l` 已经足够承载当前需求

当前官方公开链接本身就已经统一输出到 `/l/:slug`。

这意味着：

- 自定义域名首发不需要再开放 `/c`、`/s`
- 不需要为了“未来也许会用到”先把多前缀方案做进去
- 只要把 `host -> workspace` 映射打通，就足够落地第一版

### 3.3 这样能把复杂度压到最低

收口后，域名能力只需要解决一条主链：

1. 用户绑定一个 `go` 域名
2. 系统验证 DNS 与证书
3. 正式链接从 `go.naviora.link/l/:slug` 切到 `{custom_domain}/l/:slug`

不用再同时考虑：

- `go` 和 `page` 两类域名
- 不同 surface 对应不同项目
- `/l` 和 `/c` 的分流策略
- 内容域名下的 preview 跳转

---

## 4. 首发范围

### 4.1 V1 要做的事

首发建议只做：

- 用户绑定 1 个默认自定义域名
- 该域名只用于正式公开入口
- 正式公开入口统一走 `/l/:slug`
- 验证成功后，链接生成优先使用这个域名

### 4.2 V1 不做的事

明确不做：

- `page` 自定义域名
- 同一工作区绑定多个不同类型域名
- 单条 entry 指定独立域名
- Preview 走自定义域名
- 自定义域名下开放 `/c`、`/s` 等其他路径
- 同一个主域名按路径拆成多种 surface

---

## 5. 产品规则建议

### 5.1 绑定粒度

第一阶段继续按“工作区级默认域名”实现：

- 一个工作区最多绑定一个默认自定义域名
- 工作区下所有正式公开链接默认使用该域名

如果未来真的有多品牌需求，再扩展到：

- 一个工作区多个域名
- 单条 entry 选域名

但这不属于当前版本。

### 5.2 套餐建议

建议：

- `Free`
  不支持自定义域名
- `Starter`
  支持 1 个自定义 `go` 域名
- `Premium`
  首发阶段仍然和 `Starter` 同口径，先不因为套餐提前引入多域名模型

### 5.3 域名形态建议

首发优先支持子域名：

- `go.brand.com`
- `qr.brand.com`
- `link.brand.com`

不建议第一版就优先做：

- 根域名，如 `brand.com`
- 泛域名，如 `*.brand.com`

原因：

- 子域名的 DNS 指引和 Vercel 绑定更稳定
- 客户操作门槛更低
- 首发更容易降低支持成本

---

## 6. 数据模型建议

因为只保留一种域名类型，数据模型也应同步收窄。

### 6.1 推荐表：`workspace_domains`

建议字段：

- `id`
- `workspace_id`
- `domain`
- `status`
  - `pending`
  - `verifying`
  - `active`
  - `failed`
  - `removed`
- `is_primary`
- `verification_method`
  - `cname`
  - `txt`
  - `apex_a_record`
- `verification_name`
- `verification_value`
- `ssl_status`
- `last_checked_at`
- `verified_at`
- `created_at`
- `updated_at`

### 6.2 不再保留的字段

由于不再支持 `page` 域名，建议不要再引入以下模型复杂度：

- `surface`
- `go/page` 两种域名类型枚举
- `workspace_page_domain`
- `entry_domain_overrides`

如果将来真的要扩展，不如在未来版本按新规则新增字段，而不是现在先预埋一堆永远不用的分支。

### 6.3 索引建议

- unique(`domain`)
- index(`workspace_id`, `status`)
- index(`workspace_id`, `is_primary`)

---

## 7. 域名绑定流程

推荐流程如下：

1. 用户在后台输入自定义域名
2. 系统校验格式
3. 系统检查是否已被其他工作区占用
4. 服务端调用 Vercel Domains API，把域名添加到公开项目
5. 把 Vercel 返回的验证信息写入 `workspace_domains`
6. 前端展示 DNS 配置说明
7. 用户完成 DNS 配置
8. 用户点击“重新验证”或系统后台轮询验证
9. 验证成功后，把状态改为 `active`
10. 后续正式链接统一优先使用该域名

这里的“公开项目”只指当前承载 `go` 入口的公开层，不再区分 page 项目。

---

## 8. 运行时路由改造

### 8.1 当前问题

现在公开访问层主要依赖固定 host 常量，例如：

- `naviora.link`
- `www.naviora.link`
- `go.naviora.link`

这意味着当前代码还不能识别“动态绑定进来的客户域名”。

### 8.2 改造方向

需要增加一层：

- `host -> workspace` 映射解析

而不是以前那种：

- `host -> workspace + surface`

因为 `surface` 已经不再需要。

### 8.3 运行时需要支持的判断

运行时只需要支持：

- 当前 host 是否是 Naviora 官方域名
- 当前 host 是否是某个工作区的自定义 `go` 域名
- 当前路径是否为允许的正式入口路径 `/l/:slug`
- 当前路径是否为系统 preview 路径 `/preview/:token`

### 8.4 缓存建议

自定义域名解析是热路径，不建议每个请求都直接查数据库。

推荐：

- Supabase 存正式数据
- Edge Config / Redis / Runtime Cache 存域名映射缓存

建议缓存结构：

- key: `domain:go.brand.com`
- value:
  - `workspace_id`
  - `status`
  - `is_primary`

域名验证成功、删除、切换主域名时，主动刷新缓存。

---

## 9. 链接生成策略

### 9.1 当前策略

当前官方公开链接应统一输出为：

- `https://go.naviora.link/l/:slug`

### 9.2 自定义域名启用后的策略

如果工作区已绑定自定义域名，正式公开链接改为：

- `https://{workspace_domain}/l/:slug`

如果工作区未绑定，继续回退为：

- `https://go.naviora.link/l/:slug`

### 9.3 Preview 策略

Preview 永远不走自定义域名：

- `https://go.naviora.link/preview/:token`

---

## 10. 安全与限制

建议增加以下约束：

- 一个域名只能绑定到一个工作区
- 未验证成功的域名不能参与正式 URL 生成
- 被删除或停用的域名立即失效并回退系统域名
- Preview 禁止使用自定义域名
- 密码保护、访问统计、套餐限流仍然以统一入口层逻辑为准
- 自定义域名首发只允许 `/l/:slug`

这意味着：

- 即使系统内部还有历史兼容路径
- 自定义域名功能本身也不向外承诺这些路径

---

## 11. 管理后台建议

后台建议新增“自定义域名”模块，至少包括：

- 域名列表
- 添加域名
- 查看验证状态
- DNS 配置说明
- 重新验证
- 设为默认域名
- 删除域名

每条域名建议展示：

- 域名
- 当前状态
- 是否默认
- DNS 指引
- SSL 状态
- 最近验证时间

不需要展示：

- surface 类型
- page/go 二选一

因为这些概念已经从产品里移除。

---

## 12. 后续扩展边界

### 12.1 什么时候再考虑新路径

只有当 `/l/:slug` 明确不够用时，再评估新增路径前缀，例如：

- `/v/:slug`
- `/p/:slug`
- `/m/:slug`

但那会是“内容模块演进”能力，不属于当前自定义域名首发范围。

### 12.2 暂不考虑的方向

当前明确不进入路线图：

- `page` 自定义域名
- “同一主域名同时承载 go + page”
- 单条 entry 指定域名
- 多域名、多品牌复杂分发

---

## 13. 推荐实施顺序

### Phase 1

- 新增 `workspace_domains`
- 仅支持一个工作区默认自定义域名
- 接入 Vercel Domains API
- 做域名验证与状态页
- 正式链接优先使用该域名
- 自定义域名仅允许 `/l/:slug`

### Phase 2

- 域名映射缓存
- 管理后台完善
- 域名切换和删除后的自动回退逻辑
- 套餐能力绑定

### Phase 3

- 如果以后确实需要更多内容模块，再评估是否引入新的路径前缀
- 但不恢复 `page` 自定义域名方案

---

## 14. 当前结论

最稳、最符合当前产品方向的方案是：

- 只做 `go` 自定义域名
- 只生成 `/l/:slug`
- 不保留 `page` 自定义域名设计
- 不预埋 `go + page` 双 surface 逻辑
- 不提前开放 `/c`、`/s` 等其他路径策略

这样能最大程度降低：

- 产品心智成本
- 开发实现复杂度
- 运行时路由分支
- 后续维护负担

也更符合当前已经明确的方向：  
`page` 域名不会启用，自定义域名能力只服务于统一的公开入口层。
